# RFCs

Requests for Comments propose changes to working Intelligence, repository structure, mission scope, or operating rules before adoption.

RFCs now propose changes to working frameworks, systems, repository architecture, or Canon material. They do not make decisions by themselves.

## What Belongs Here

Reviewable proposals with motivation, evidence, alternatives, counterarguments, affected areas, and accountable decision owners.

## What Does Not Belong Here

Accepted decisions, current system specifications, raw research, procedures, or Canon chapters.

## How Documents Enter

A supported research finding, operational problem, Canon challenge, or system-design need becomes an RFC when the proposed change and review boundary are explicit.

## How Documents Leave or Become Superseded

An RFC is accepted, rejected, deferred, superseded, or returned to research. Accepted outcomes link to `DEC-*` or ADR records and affected specifications.

## Process

1. State the proposal and motivation.
2. Link available evidence.
3. Preserve counterarguments and open questions.
4. Record an explicit decision.
5. If accepted, update the affected canonical documents, versions, dependencies, and revision logs.

## Related Folders

- `../research/` supplies evidence.
- `../decisions/` records institutional outcomes.
- `../adrs/` records technical outcomes.
- `../systems/` implements accepted changes.
- `../canon/` receives reviewed synthesis.
